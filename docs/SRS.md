## 1. 📖 Introduction

### 1.1 Purpose
This document specifies the software requirements for the **Smart Classroom Face Attendance System**, a high-performance web platform utilizing facial recognition biometrics to automate attendance tracking. This specification details the functional, non-functional, external interface, and database requirements for developers, system architects, and academic stakeholders.

### 1.2 Document Conventions
- **IEEE 830 Standard**: Structured according to standard software engineering guidelines.
- **RBAC**: Role-Based Access Control (`ADMIN`, `TEACHER`, `STUDENT`).
- **128-D Vector**: A 128-dimensional floating-point array generated by the OpenCV SFace ArcFace neural network.
- **Class `.pkl`**: A Python pickle binary database file storing student face feature vectors scoped strictly to a single class section.
- **V1 (MVP Base)**: Single active class attendance session over HTTP REST API.
- **V2 (Scale Engine)**: Dedicated multi-threading frame processing worker pool with section-isolated multi-PKL indexing and WebSockets.

### 1.3 Intended Audience
- **Full-Stack MERN Developers**: Building Node/Express REST APIs, Mongoose data models, and React dashboards.
- **AI/ML Engineers**: Maintaining OpenCV YuNet detection, SFace recognition microservices, thread pool executors, and `.pkl` vector engines.
- **System Administrators & Department Heads**: Managing user accounts, classroom schedules, and institutions.

### 1.4 Project Scope
The system provides a web application replacing manual paper roll calls. It captures live camera feeds, aligns faces using 5-point facial landmarks, extracts 128-D embeddings, matches them against class-isolated vector databases (`<class_id>_db.pkl`), and logs attendance instantly into MongoDB.

### 3.1 Module 1: Authentication & User Management
- **FR-1.1**: The system shall support secure user login using Email or Student Roll Number and Password.
- **FR-1.2**: Upon successful authentication, the Express backend shall issue a signed JSON Web Token (JWT) containing `userId`, `role`, and `department` expiring in 8 hours.
- **FR-1.3**: User passwords shall be hashed using `bcrypt` with a minimum salt factor of 10.
- **FR-1.4**: System Admins shall be able to create, edit, deactivate, and reset credentials for Teacher and Student accounts.

---

### 3.2 Module 2: Department, Course & Roster Mapping
- **FR-2.1**: System Admins shall create and manage Academic Departments (e.g., `Computer Science`, `Electrical Engineering`).
- **FR-2.2**: System Admins shall create Course Sections (e.g., `CS101 - Data Structures Sec A`).
- **FR-2.3**: System Admins shall assign a primary Teacher to each Course Section.
- **FR-2.4**: Teachers and Admins shall map enrolled Students to specific Class Rosters.

---

### 3.3 Module 3: Student Facial Enrollment Engine
- **FR-3.1**: Students or Admins shall enroll face biometrics by uploading a photo or capturing a snapshot via webcam.
- **FR-3.2**: The ML service shall process images through **OpenCV YuNet** to detect faces and extract 5-point facial landmarks (eyes, nose, mouth corners).
- **FR-3.3**: The ML service shall normalize crops to $112 \times 112$ pixels and generate a 128-dimensional ArcFace vector embedding using **OpenCV SFace**.
- **FR-3.4**: Vectors shall be saved to MongoDB (`user.embeddings`) and compiled into the target class pickle database (`ml/class_dbs/<class_id>_db.pkl`).
- **FR-3.5**: The system shall reject low-quality photos (e.g., no face detected, multiple faces detected, blur score below threshold).

---

### 3.4 Module 4 (V1): Single-Class Live Attendance & Modal Engine
- **FR-4.1**: Teachers start a session by selecting a class section, triggering `POST /api/ml/load-class-db`.
- **FR-4.2**: The frontend launches a live webcam modal capturing frames at 30 FPS and sending base64 payloads to `POST /api/ml/process-frame`.
- **FR-4.3**: The ML microservice calculates batch dot-product matrix multiplication ($\mathbf{M} \cdot \mathbf{v}^T$) against active class vectors.
- **FR-4.4**: If similarity score $\ge 0.36$, the state machine transitions from `SCANNING` to `LOCKED_CONFIRMED`.
- **FR-4.5**: In `LOCKED_CONFIRMED` state, the UI freezes on a GREEN visual confirmation banner ("`PRESENT: Hari Haran (21CS042)`") for **7.0 seconds** before automatically resetting for the next student.
- **FR-4.6**: Confirmed records post instantly to MongoDB with `classId`, `rollNumber`, `studentName`, `timestamp`, `date`, `status: "PRESENT"`, and `confidence`.

---

### 3.5 Module 4 (V2): Enterprise Multi-PKL & Multi-Threaded Engine
- **FR-4.7 (Multi-PKL Indexing)**: The ML service shall maintain section-isolated vector database files (`ml/class_dbs/<class_id>_db.pkl`). It shall support loading and indexing multiple `.pkl` files simultaneously in RAM without cross-class vector collision.
- **FR-4.8 (Dedicated Worker Multi-Threading)**: The ML microservice shall utilize a `ThreadPoolExecutor` worker pool. Frame decoding, face detection, alignment, and matrix multiplication shall run asynchronously in dedicated background threads, ensuring main HTTP/WebSocket request handlers remain zero-latency and non-blocking.
- **FR-4.9 (LRU Vector Caching)**: The system shall keep active class matrices cached in memory using an LRU (Least Recently Used) cache policy with automatic background re-syncing from MongoDB.
- **FR-4.10 (WebSocket Real-Time Broadcast)**: Recognized presence events shall be emitted via WebSockets to connected Teacher dashboards and Administrative monitors instantly.

### 3.6 Module 5: Attendance Analytics & Reports

## ⚡ 4. Non-Functional Requirements

### 4.1 Performance Requirements
- **V1 Latency**: Single frame detection and vector match execution $\le 45\text{ ms}$.
- **V2 Latency**: Frame matching in dedicated thread pool $\le 15\text{ ms}$.
- **Frame Throughput**: System handles 30–60 FPS live video stream without frame buildup.
- **Matrix Matching**: Search complexity is $O(1)$ batch matrix multiplication scoped to 30–60 students per section.

### 4.2 Security & Data Privacy
- **Vector Anonymization**: 128-D floating-point embeddings cannot be reverse-engineered to reconstruct human face images.
- **Authentication**: JWT tokens signed with SHA-256 algorithm and 8-hour expiry.
- **Encryption**: Passwords hashed with `bcrypt` (10 salt rounds). MongoDB connection strings stored strictly in `.env` configuration files.

### 4.3 Reliability & Resilience
- **State Recovery**: Auto-resets to `SCANNING` mode if webcam stream drops or frame decoding fails.
- **PKL Auto-Rebuild**: If a `.pkl` vector database is missing or corrupt, the system automatically reconstructs it from MongoDB student vector arrays.

## 📊 5. Data Dictionary & Database Schemas

### 5.1 MongoDB Collections
- `users`: User profiles (`name`, `email`, `password`, `role`, `department`, `rollNumber`, `embeddings`).
- `classes`: Class sections (`classId`, `className`, `department`, `teacherId`, `studentIds`).
- `attendances`: Daily records (`classId`, `studentId`, `rollNumber`, `date`, `status`, `confidence`, `timestamp`).
- `auditlogs`: Manual override logs (`action`, `performedBy`, `targetUser`, `timestamp`).

### 5.2 Python PKL File Schema (`ml/class_dbs/<class_id>_db.pkl`)

{
    "CLASS_ID": "CS101_SEC_A",
    "LAST_UPDATED": "2026-08-26T20:00:00Z",
    "STUDENTS": {

            "name": "Hari Haran",
            "department": "Computer Science",
            "features": [ [0.012, -0.045, ..., 0.128] ] # 128-D vector
        }
    }
}
